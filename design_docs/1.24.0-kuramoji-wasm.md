# kuromoji-wasm Implementation Plan

## Overview

This document is a complete implementation plan for replacing `kuromoji.js` in
the `go-reader` app with a Rust/WASM drop-in replacement. The goal is to
eliminate the ~5 second startup time (measured from browser cache) caused by
kuromoji parsing its IPAdic binary dictionary files in JavaScript.

The replacement is a new Rust crate (`kuromoji-wasm`) that:

- Uses [Lindera](https://github.com/lindera-morphology/lindera) for Japanese
  morphological analysis with the IPAdic dictionary bundled into the WASM binary
- Exposes exactly the same JavaScript API as `kuromoji.js` so `index.html`
  requires only a single one-line change
- Is compiled to WASM using `wasm-pack`
- Lives in a `kuromoji-wasm/` subdirectory inside the existing `go-reader`
  repository

**No changes to `index.html` logic, CSS, JMdict loading, or any other part of
the app are required.**

______________________________________________________________________

## Background and motivation

`go-reader` is a single-file static web app (`index.html`) that tokenizes
Japanese text in the browser using `kuromoji.js` and looks up morphemes in a
bundled JMdict JSON dictionary. See `docs/architecture.md` for a full breakdown.

The startup sequence currently is:

1. Load `kuromoji.js` (~1 MB)
2. Load kuromoji's IPAdic binary dictionary files from `dict/*.dat.gz` (~5 files,
   several MB total)
3. kuromoji parses those binary files in JavaScript — **this is the bottleneck**
4. Load the selected JMdict JSON (`dict/jmdict-full.json.gz` or
   `dict/jmdict-ultra-compact.json.gz`) in parallel with step 2–3
5. App becomes interactive

Step 3 takes ~5 seconds even from cache on a modern machine. Steps 1, 2, and 4
are fast once cached. Replacing kuromoji with a Rust/WASM implementation that
bundles IPAdic internally eliminates steps 1–3 entirely — WASM initialisation
and dictionary loading happen in native code at native speed.

## The kuromoji.js API surface used by go-reader

Read `index.html` carefully and find every reference to `kuromoji`. The full
API the app uses is:

```js
// Initialisation — called once at startup
kuromoji.builder({ dicPath: 'dict/' }).build(function(err, tokenizer) {
    // err is null on success, an Error on failure
    // tokenizer is ready to use
});

// Tokenisation — called on every text change (debounced 300ms)
const tokens = tokenizer.tokenize(text);
```

Each token object used by the app has exactly these five fields:

| Field          | IPAdic meaning              | Example      |
| -------------- | --------------------------- | ------------ |
| `surface_form` | 表層形 — text as it appears | `食べました` |
| `reading`      | 読み — katakana reading     | `タベマシタ` |
| `basic_form`   | 基本形 — dictionary form    | `食べる`     |
| `pos`          | 品詞 — part of speech       | `動詞`       |
| `pos_detail_1` | 品詞細分類1 — POS subtype   | `自立`       |

No other fields are used. The WASM replacement only needs to return these five.

## Lindera IPAdic detail array indices

Lindera returns IPAdic feature data as a `Vec<&str>` (or `Vec<String>`) in this
fixed order (confirm by inspecting Lindera source or running a test):

```
[0]  pos            品詞
[1]  pos_detail_1   品詞細分類1
[2]  pos_detail_2   品詞細分類2
[3]  pos_detail_3   品詞細分類3
[4]  conjugated_type 活用型
[5]  conjugated_form 活用形
[6]  basic_form     基本形
[7]  reading        読み
[8]  pronunciation  発音
```

**This must be verified by writing a small native Rust test before building the
WASM.** Run:

```rust
// in kuromoji-wasm/src/lib.rs or a test file
#[cfg(test)]
mod tests {
    use lindera::tokenizer::Tokenizer;
    #[test]
    fn check_detail_indices() {
        let tokenizer = Tokenizer::new().unwrap();
        let tokens = tokenizer.tokenize("食べました").unwrap();
        for t in &tokens {
            println!("surface: {}", t.text);
            for (i, d) in t.details().iter().enumerate() {
                println!("  [{}] {}", i, d);
            }
        }
    }
}
```

Run with `cargo test -- --nocapture` and confirm the indices above match.
Adjust the index constants in `lib.rs` if they differ.

## Critical correctness requirements

The app has specific lookup behaviour that depends on token fields being correct.
Read `docs/architecture.md` section "Lookup Logic" carefully. The following
cases **must** be verified in tests:

### 1. Basic verb conjugation

`食べました` must produce a token with `basic_form: 食べる`. This is the normal
case — kuromoji and Lindera should agree.

### 2. Godan imperative fallback

The app has a special fallback for godan imperatives that kuromoji
misanalyses as potential-form verbs. Example: `払え` — kuromoji returns
`basic_form: 払える` (potential, wrong) instead of `払う`. The app detects this
and applies a kana mapping to recover the correct dictionary form.

**Test what Lindera returns for `払え`.** If Lindera returns `basic_form: 払う`
(correct), the godan fallback in `index.html` will still trigger harmlessly but
find the word via `basic_form` first. If Lindera also returns `払える`, the
fallback is still needed. Document which case applies.

Also test: `死ね` (should return as an interjection, has its own JMdict entry).

### 3. Particles

`は`, `が`, `を`, `で`, `て`, `に` — all must have `pos: 助詞`. Verify
`pos_detail_1` matches what `index.html` expects for the `pg2` field selection:

```js
if (token.pos_detail_1 === '接続助詞' && entry.pg2) { ... }
```

`て` as a conjunctive particle must produce `pos_detail_1: 接続助詞`.

### 4. Auxiliary verbs

`です`, `ます`, `ない` — must have `pos: 助動詞`.

### 5. Unknown words

Words not in IPAdic (e.g. recent loanwords, proper nouns) — Lindera should
return them as a single token with `pos: 名詞` or similar. Verify `reading` and
`basic_form` are populated or are `*` — the app handles `*` gracefully.

### 6. Grammar dimming

`index.html` dims tokens whose `pos` is in this set:
`['助詞', '助動詞', '記号', '補助記号', '空白', 'フィラー', '句読点', '特殊']`

Verify that Lindera produces these exact Japanese POS strings for particles,
auxiliary verbs, punctuation, and whitespace. If Lindera uses different strings,
the dimming logic will break — but **do not change `index.html`** to compensate;
instead make the WASM output match what `index.html` expects.

## src/lib.rs

```rust
use js_sys::Function;
use serde::Serialize;
use wasm_bindgen::prelude::*;

// IPAdic detail indices — verify these with the native test above
// before trusting them.
const IDX_POS: usize = 0;
const IDX_POS_DETAIL_1: usize = 1;
const IDX_BASIC_FORM: usize = 6;
const IDX_READING: usize = 7;

#[derive(Serialize)]
pub struct Token {
    pub surface_form: String,
    pub reading: String,
    pub basic_form: String,
    pub pos: String,
    pub pos_detail_1: String,
}

#[wasm_bindgen]
pub struct JsTokenizer {
    inner: lindera::tokenizer::Tokenizer,
}

#[wasm_bindgen]
impl JsTokenizer {
    /// tokenize(text: string): Token[]
    /// Returns a JS array of plain objects matching the kuromoji token shape.
    pub fn tokenize(&mut self, text: &str) -> Result<JsValue, JsValue> {
        let tokens = self
            .inner
            .tokenize(text)
            .map_err(|e| JsValue::from_str(&e.to_string()))?;

        let out: Vec<Token> = tokens
            .iter()
            .map(|t| {
                let d = t.details().unwrap_or_default();
                Token {
                    surface_form: t.text.to_string(),
                    reading:      d.get(IDX_READING).unwrap_or(&"*").to_string(),
                    basic_form:   d.get(IDX_BASIC_FORM).unwrap_or(&"*").to_string(),
                    pos:          d.get(IDX_POS).unwrap_or(&"*").to_string(),
                    pos_detail_1: d.get(IDX_POS_DETAIL_1).unwrap_or(&"*").to_string(),
                }
            })
            .collect();

        serde_wasm_bindgen::to_value(&out).map_err(|e| JsValue::from_str(&e.to_string()))
    }
}

/// builder({ dicPath }) — dicPath is accepted and ignored; IPAdic is bundled.
#[wasm_bindgen]
pub fn builder(_opts: JsValue) -> Builder {
    Builder
}

#[wasm_bindgen]
pub struct Builder;

#[wasm_bindgen]
impl Builder {
    /// build(callback: function(err, tokenizer))
    /// Matches the kuromoji.builder().build(cb) signature exactly.
    pub fn build(&self, callback: &Function) -> Result<(), JsValue> {
        // Build the Lindera tokenizer with bundled IPAdic.
        // Exact API depends on Lindera version — adjust if needed.
        match build_tokenizer() {
            Ok(inner) => {
                let tok = JsTokenizer { inner };
                let js_tok = JsValue::from(tok);
                callback.call2(&JsValue::NULL, &JsValue::NULL, &js_tok)?;
            }
            Err(e) => {
                let err = JsValue::from_str(&e.to_string());
                callback.call2(&JsValue::NULL, &err, &JsValue::UNDEFINED)?;
            }
        }
        Ok(())
    }
}

fn build_tokenizer() -> Result<lindera::tokenizer::Tokenizer, Box<dyn std::error::Error>> {
    // Adjust this to the actual Lindera 0.32 API.
    // Check Lindera's docs/examples for the correct way to build a tokenizer
    // with the bundled ipadic feature — it may be:
    //   Tokenizer::new()
    //   Tokenizer::with_config(TokenizerConfig::default())
    //   Tokenizer::from_config(...)
    // Confirm by reading Lindera source or examples.
    let tokenizer = lindera::tokenizer::Tokenizer::new()?;
    Ok(tokenizer)
}
```

**Note:** The exact Lindera API for constructing a tokenizer with a bundled
dictionary has changed across versions. Before writing the final code, check
Lindera's documentation or source for version 0.32 (or whichever version
resolves). The `build_tokenizer()` function is where this needs to be resolved.

## JS shim — pkg/kuromoji_wasm.js

`wasm-pack` generates a `pkg/` directory. The JS shim wraps the generated
module to expose `window.kuromoji` with the exact same API as the existing
`kuromoji.js`.

After `wasm-pack build`, create (or append to) `pkg/kuromoji_wasm.js`:

```js
// kuromoji-wasm: drop-in replacement for kuromoji.js
// Exposes window.kuromoji with the same builder/build/tokenize API.

import init, { builder as _builder } from './kuromoji_wasm_bg.js';

let _ready = false;
const _queue = [];

// Initialise the WASM module. This replaces the kuromoji dictionary load.
init().then(() => {
    _ready = true;
    _queue.forEach(fn => fn());
    _queue.length = 0;
});

window.kuromoji = {
    builder(opts) {
        return {
            build(callback) {
                const go = () => {
                    try {
                        _builder(opts).build(callback);
                    } catch (e) {
                        callback(e, null);
                    }
                };
                _ready ? go() : _queue.push(go);
            }
        };
    }
};
```

**Important:** `wasm-pack --target web` generates ES module output. The shim
uses `import`, so the `<script>` tag in `index.html` must be `type="module"`.
See the index.html change below.

## index.html change

Find the existing script tag that loads kuromoji (it will look like):

```html
<script src="kuromoji.js"></script>
```

Replace it with:

```html
<script type="module" src="pkg/kuromoji_wasm.js"></script>
```

**This is the only change to `index.html`.**

However, there is one subtlety: `type="module"` scripts are deferred by default.
The existing code likely waits for the kuromoji `build` callback before enabling
the UI, so this should be safe. Verify that the app's startup flow still works —
specifically that the "loading" status message appears and the UI is correctly
disabled until the WASM tokenizer is ready, just as it was with kuromoji.

If the module loading order causes any issue (e.g. `window.kuromoji` not defined
when `index.html`'s inline script runs), the fix is to move the WASM
initialisation inline or use a non-module script that manually calls the init
function. Investigate if this occurs.

## Correctness tests

Create `kuromoji-wasm/tests/tokenize.rs`. These run as native Rust tests
(`cargo test`), not in the browser. They verify the token output matches what
`index.html` expects.

```rust
use kuromoji_wasm::tokenize_native;
// tokenize_native() is a non-wasm-bindgen function exposed from lib.rs
// for testing purposes only. Add it to lib.rs:
//
//   #[cfg(not(target_arch = "wasm32"))]
//   pub fn tokenize_native(text: &str) -> Vec<crate::Token> { ... }

#[test]
fn basic_verb_conjugation() {
    let tokens = tokenize_native("食べました");
    let t = tokens.iter().find(|t| t.surface_form == "食べ").unwrap();
    assert_eq!(t.basic_form, "食べる");
    assert_eq!(t.pos, "動詞");
}

#[test]
fn particle_ha() {
    let tokens = tokenize_native("私は");
    let t = tokens.iter().find(|t| t.surface_form == "は").unwrap();
    assert_eq!(t.pos, "助詞");
}

#[test]
fn conjunctive_particle_te() {
    // て as conjunctive particle must be pos_detail_1: 接続助詞
    // so the pg2 lookup in index.html works correctly
    let tokens = tokenize_native("食べて");
    let t = tokens.iter().find(|t| t.surface_form == "て").unwrap();
    assert_eq!(t.pos, "助詞");
    assert_eq!(t.pos_detail_1, "接続助詞");
}

#[test]
fn auxiliary_desu() {
    let tokens = tokenize_native("です");
    let t = &tokens[0];
    assert_eq!(t.pos, "助動詞");
}

#[test]
fn godan_imperative_harae() {
    // 払え — kuromoji misanalyses as potential 払える.
    // Test what Lindera returns. Document the result.
    // If basic_form is 払う (correct), the app's godan fallback is a no-op.
    // If basic_form is 払える (same as kuromoji), the app's fallback still works.
    let tokens = tokenize_native("払え");
    let t = &tokens[0];
    println!("払え -> basic_form: {}, pos: {}", t.basic_form, t.pos);
    // Assert whichever is correct once you know:
    // assert_eq!(t.basic_form, "払う");  // if Lindera is correct
    // assert_eq!(t.basic_form, "払える"); // if Lindera matches kuromoji
}

#[test]
fn shiné_interjection() {
    // 死ね has its own JMdict entry as an interjection
    let tokens = tokenize_native("死ね");
    let t = &tokens[0];
    println!("死ね -> basic_form: {}, pos: {}", t.basic_form, t.pos);
}

#[test]
fn katakana_reading_returned() {
    // Readings must be katakana (the app calls toHiragana() on them)
    let tokens = tokenize_native("日本語");
    let t = tokens.iter().find(|t| t.surface_form == "日本語").unwrap();
    assert!(t.reading.chars().all(|c| {
        // katakana range U+30A0–U+30FF or * for unknown
        (c >= '\u{30A0}' && c <= '\u{30FF}') || c == '*'
    }), "reading should be katakana, got: {}", t.reading);
}

#[test]
fn unknown_word() {
    // A word not in IPAdic — should not panic, reading/basic_form may be *
    let tokens = tokenize_native("ナントカカントカ");
    assert!(!tokens.is_empty());
}
```

## Startup time benchmark

After a working build, measure startup time as follows:

1. Serve the app locally with `just serve`
2. Open browser devtools → Network tab → disable cache
3. Hard reload — measure time from navigation start to the first tokenization
   completing (the app shows tokenized text)
4. Re-enable cache, reload several times — measure cached startup time
5. Compare against the current kuromoji.js baseline (~5 seconds from cache)

Record both cold (no cache) and warm (from cache) times in a comment at the
top of `docs/architecture.md`.

### Results (measured 2026-06-06, localhost, Chrome, localStorage text pre-loaded)

Times are `tokenizer ready / app usable` (both logged via `console.log` + `performance.now()`).
The gap between the two is ~50–80 ms in both cases — JMdict finishes almost immediately after
the tokenizer, meaning they race neck and neck.

#### kuromoji.js baseline

|                           | Run 1       | Run 2       | Run 3       | Avg            |
| ------------------------- | ----------- | ----------- | ----------- | -------------- |
| Cold — tokenizer / usable | 4962 / 5022 | 5084 / 5192 | 5063 / 5155 | 5036 / 5123 ms |
| Warm — tokenizer / usable | 4914 / 5006 | 5124 / 5185 | 4676 / 4731 | 4905 / 4974 ms |

#### kuromoji-wasm

|                           | Run 1       | Run 2       | Run 3       | Avg            |
| ------------------------- | ----------- | ----------- | ----------- | -------------- |
| Cold — tokenizer / usable | 3623 / 3667 | 3641 / 3714 | 3935 / 4002 | 3733 / 3794 ms |
| Warm — tokenizer / usable | 3408 / 3441 | 2985 / 3051 | 3105 / 3140 | 3166 / 3211 ms |

#### Summary

|                                    | Before (usable avg) | After (usable avg) | Saving          |
| ---------------------------------- | ------------------- | ------------------ | --------------- |
| Cold — empty cache and hard reload | 5123 ms             | 3794 ms            | **~1.3s (26%)** |
| Warm — normal refresh with cache   | 4974 ms             | 3211 ms            | **~1.8s (35%)** |

The warm improvement is larger because with cache the dict files load fast and JS parsing of the
IPAdic binary was the only remaining bottleneck — which WASM eliminates entirely. The ~5s
estimate in the design doc was for kuromoji in isolation; the end-to-end time is higher because
JMdict loading runs in parallel and sets a ~3s floor.

## Resolving open questions

The following must be answered by inspecting the actual code and running tests.
Do not assume — verify each one.

### Q1: Exact Lindera version and feature flag

Check crates.io for the latest stable Lindera release. The `ipadic` feature may
be named differently (e.g. `ipadic-bundled`, `lindera-ipadic`). Run
`cargo add lindera` and check what features are available:

```bash
cargo add lindera
cat Cargo.lock | grep lindera
```

Or check https://crates.io/crates/lindera for the features list.

### Q2: Lindera tokenizer construction API

The API for creating a `Tokenizer` with bundled IPAdic has changed between
Lindera versions. Read the Lindera source at the resolved version to find the
correct constructor. It will be one of:

```rust
Tokenizer::new()
Tokenizer::with_config(config)
Tokenizer::from_config(config)
```

Check Lindera's `examples/` directory or `README.md` for the current pattern.

### Q3: Lindera's tokenize() method signature

Lindera's `tokenize()` may take `&str`, `&mut self`, or `self`. It may return
`Vec<Token>` or `Result<Vec<Token>, Error>`. Check the resolved version's API
and adjust `lib.rs` accordingly.

### Q4: Lindera Token details() method

Lindera tokens expose their IPAdic features as either:

- `token.details()` returning `Option<Vec<&str>>`
- `token.detail` as a field
- Some other accessor

Check the Lindera source at the resolved version and adjust the index access in
`lib.rs` accordingly.

### Q5: WASM binary size

After `wasm-pack build --release`, check the size of `pkg/kuromoji_wasm_bg.wasm`.
It will include the bundled IPAdic dictionary. If it is larger than ~15 MB,
consider whether the existing kuromoji approach (loading dict files separately,
from cache) is actually better for cold load. If WASM size is under ~10 MB it
is a straightforward win.

### Q6: module vs non-module script loading

Verify that changing the `<script src="kuromoji.js">` to
`<script type="module" src="pkg/kuromoji_wasm.js">` does not break the startup
sequence. Read the `index.html` JS carefully to understand how and when it
accesses `window.kuromoji`. Module scripts execute after the DOM is parsed and
are deferred; if `index.html`'s inline JS calls `kuromoji.builder()` during
parse, `window.kuromoji` may not be defined yet. The existing code already
handles async initialisation (the kuromoji `build` callback), so this is likely
fine — but verify.

## Acceptance criteria

The implementation is complete when:

1. `cargo test` in `kuromoji-wasm/` passes all tests
2. `wasm-pack build --target web --release --out-dir ../pkg` succeeds
3. The app loads and functions identically to the current version in a browser
4. Startup time from cache is measurably faster than the ~5 second baseline
5. All existing `just lint` and `just test` commands still pass
6. `docs/architecture.md` reflects the new architecture
7. `LICENSE-IPADIC` is present in the repo root
8. `/pkg/` and `/kuromoji-wasm/target/` are in `.gitignore`
