# jmdict-wasm Implementation Plan

## Benchmark results

Timings measured in Chrome on the dev machine (`localhost`, full dictionary).

### Before jmdict-wasm (JSON fetch + parse)

| Metric          | Cold      | Warm      |
| --------------- | --------- | --------- |
| jmdict usable   | ~3 500 ms | ~3 000 ms |
| tokenizer ready | ~1 700 ms | ~1 600 ms |
| first morphemes | ~4 000 ms | ~3 500 ms |

JMdict was the dominant bottleneck: `JSON.parse()` of 41 MB took ~3 s regardless of
cache state.

### After jmdict-wasm (binary search over static WASM bytes)

| Metric            | Cold         | Warm         |
| ----------------- | ------------ | ------------ |
| jmdict wasm ready | 1 358 ms     | 1 520 ms     |
| tokenizer ready   | 1 802 ms     | 1 611 ms     |
| first morphemes   | **1 874 ms** | **1 650 ms** |

JMdict is now off the critical path — it completes before the tokenizer on both cold
and warm loads. The tokenizer (kuromoji-wasm, ~1.6–1.8 s) is the remaining floor.

### Implementation notes

The first approach (postcard-serialized `HashMap` constructed at `mod.init()`) gave
no improvement — building 461 k entries in WASM took ~2 s, matching the old
`JSON.parse()` cost. The fix was switching to a sorted binary index embedded in the
WASM data section with binary search at lookup time (zero init cost). The full-dict
WASM (37 MB / 13 MB gzip) is now served gzip-compressed by `local_serve.py` via a
pre-built `.wasm.gz` sidecar.

## Overview

This document is a complete implementation plan for replacing the runtime JSON
parse of the JMdict dictionary with a Rust/WASM binary that has the dictionary
compiled in ahead of time.

The current bottleneck: `compact_jmdict.py` produces a gzip-compressed JSON
file (`jmdict-full.json.gz`, 7.7 MB / 41 MB uncompressed; `jmdict-ultra-compact.json.gz`,
2.6 MB / 12 MB uncompressed) that the browser fetches and parses with `JSON.parse()`
at startup. That parse takes ~3 seconds on a modern machine — the dominant floor after
kuromoji-wasm eliminated the tokenizer cost.

The fix is the same pattern used for kuromoji-wasm: move the parse from just-in-time
(browser, every load) to ahead-of-time (build machine, once). The dictionary is
compiled into a Rust data structure at `wasm-pack build` time and baked into the WASM
binary. At runtime the browser receives a binary blob it can query directly with no
parsing step.

The replacement is a new Rust crate (`jmdict-wasm`) that:

- Reads the compact JMdict JSON produced by `compact_jmdict.py` at **build time**
  using a `build.rs` script
- Stores the dictionary as a compile-time perfect hash map using the `phf` crate
- Exposes a single `lookup(word: &str) -> JsValue` function returning a JS object
  with the same shape as the current JSON entries
- Lives in a `jmdict-wasm/` subdirectory inside the existing `go-reader` repository

**No changes to `index.html` lookup logic, CSS, or any other part of the app are
required beyond replacing the fetch-and-parse call.**

## Background

### Current load sequence (after kuromoji-wasm)

1. Load `kuromoji_shim.js` and `japanese-ranges.js`
2. WASM tokenizer initialises (~3.2 s warm, ~3.7 s cold) ← already fast
3. **Fetch `jmdict-full.json.gz` (7.7 MB), decompress, `JSON.parse()` (~3 s)** ← bottleneck
4. App becomes interactive

Steps 2 and 3 race in parallel. Step 3 is now the sole bottleneck.

### Why ahead-of-time compilation works here

`compact_jmdict.py` already does the expensive structural work: filtering, merging
senses, building the `pg`/`pg2` grammar glosses. The output is a flat
`{ word: entry }` map. The browser's only job is to load that map into memory and
answer `lookup(word)` calls. Moving that representation into a pre-built binary
eliminates the parse entirely — the map is ready the moment the WASM module is
instantiated, which costs well under 100 ms (as seen with kuromoji-wasm).

**In scope:**

- New `jmdict-wasm/` Rust crate
- `build.rs` that reads `dict/jmdict-ultra-compact.json.gz` and

- JS shim replacing the fetch-and-parse in `index.html` with a `lookup()` call

- `.gitignore` additions for `jmdict-wasm/target/` and `pkg/jmdict_*`

**Out of scope:**

- Changes to `compact_jmdict.py` or the JMdict source pipeline
- Changes to tokenization, UI, or any lookup logic beyond the load path
- Combining jmdict-wasm and kuromoji-wasm into a single crate

## The JMdict API surface used by go-reader

Read `index.html` carefully. The complete API is:

```js
// Load (currently fetch + JSON.parse):
jmdict = await res.json();  // or manual DecompressionStream path

// Lookup by word (called on every morpheme click/hover):
const entry = jmdict[base] || jmdict[token.surface_form];

// Existence check (called during analysis):
if (!candidates.some(w => jmdict[w])) { ... }
```

Each entry has this shape (all fields optional except `g`):

```js
{
  p:   ["n", "vs"],          // POS tags — array of JMdict tag strings
  g:   [["gloss1", "gloss2"], ["alt gloss"]], // sense groups
  pg:  ["particle gloss"],   // grammar/particle glosses (35 981 entries)
  pg2: ["alternative gloss"] // secondary grammar gloss (25 entries only)
}
```

The WASM must return objects with exactly this shape. `p`, `pg`, and `pg2` may
be absent (treat as empty/null in JS).

## Data sizes

| File                           | Compressed | Uncompressed | Keys    |
| ------------------------------ | ---------- | ------------ | ------- |
| `jmdict-ultra-compact.json.gz` | 2.6 MB     | 12 MB        | 84 751  |
| `jmdict-full.json.gz`          | 7.7 MB     | 41 MB        | 461 048 |

The ultra-compact WASM will be significantly smaller than the full one. Both
should be built so the existing dictionary-mode setting continues to work.

______________________________________________________________________

## Design: one WASM, two modes

The simplest approach is **two separate WASM binaries** — one per dictionary mode.
`index.html` already selects the dictionary file by mode; it would instead select
the WASM file by mode. Each binary only pays for the data it contains.

Alternatively, **one WASM with two lookup functions** (`lookup_ultra` /
`lookup_full`) works but doubles the binary size.

Recommendation: **two separate binaries**, mirroring the current two-file approach.

```
pkg/
  jmdict_ultra_wasm.js
  jmdict_ultra_wasm_bg.wasm   (~expected: 8–15 MB gzip)
  jmdict_full_wasm.js
  jmdict_full_wasm_bg.wasm    (~expected: 25–50 MB gzip)
```

## Rust data structure

Use the `phf` crate for a compile-time perfect hash map. `phf_codegen` runs in
`build.rs` to emit a `static MAP: phf::Map<&str, Entry>` into the generated
source.

```toml
[dependencies]
phf = { version = "0.11", features = ["macros"] }
wasm-bindgen = "0.2"
js-sys = "0.3"
serde = { version = "1", features = ["derive"] }
serde-wasm-bindgen = "0.6"

[build-dependencies]
phf_codegen = "0.11"
serde = { version = "1", features = ["derive"] }
serde_json = "1"
flate2 = "1"
```

### Entry representation

```rust
pub struct Entry {
    pub p:   &'static [&'static str],
    pub g:   &'static [&'static [&'static str]],
    pub pg:  &'static [&'static str],
    pub pg2: &'static [&'static str],
}
```

All fields are `'static` slices into string literals emitted by `phf_codegen` —
zero heap allocation, zero runtime parsing.

## build.rs

The build script reads the compact JSON, parses it into `Entry` structs, and
writes a Rust source file with the `phf::Map`.

```rust
use std::env;
use std::fs::File;
use std::io::{BufWriter, Write};
use std::path::Path;

use flate2::read::GzDecoder;
use serde::Deserialize;
use serde_json::Value;

#[derive(Deserialize)]
struct RawEntry {
    #[serde(default)] p:   Vec<String>,
    #[serde(default)] g:   Vec<Vec<String>>,
    #[serde(default)] pg:  Vec<String>,
    #[serde(default)] pg2: Vec<String>,
}

fn main() {
    // JMDICT_MODE env var selects which file to compile in (set by justfile)
    let mode = env::var("JMDICT_MODE").unwrap_or_else(|_| "ultra".to_string());
    let filename = match mode.as_str() {
        "full"  => "dict/jmdict-full.json.gz",
        _       => "dict/jmdict-ultra-compact.json.gz",
    };

    println!("cargo:rerun-if-changed={}", filename);
    println!("cargo:rerun-if-changed=build.rs");

    let repo_root = Path::new(env!("CARGO_MANIFEST_DIR")).parent().unwrap();
    let dict_path = repo_root.join(filename);

    let file = File::open(&dict_path)
        .unwrap_or_else(|_| panic!("Cannot open {}: run `just build-dict` first", dict_path.display()));
    let reader = GzDecoder::new(file);
    let raw: std::collections::HashMap<String, RawEntry> = serde_json::from_reader(reader)
        .expect("Failed to parse JMdict JSON");

    let out_dir = env::var("OUT_DIR").unwrap();
    let dest = Path::new(&out_dir).join("jmdict_map.rs");
    let mut out = BufWriter::new(File::create(&dest).unwrap());

    let mut map = phf_codegen::Map::new();
    for (word, entry) in &raw {
        // Emit each entry as a struct literal
        let p   = fmt_str_slice(&entry.p);
        let g   = fmt_str_slice_slice(&entry.g);
        let pg  = fmt_str_slice(&entry.pg);
        let pg2 = fmt_str_slice(&entry.pg2);
        map.entry(word.as_str(), &format!("Entry {{ p: {p}, g: {g}, pg: {pg}, pg2: {pg2} }}"));
    }

    writeln!(out, "static JMDICT: phf::Map<&'static str, Entry> = \n{};", map.build()).unwrap();
}

fn fmt_str_slice(v: &[String]) -> String {
    let inner: Vec<String> = v.iter().map(|s| format!("{:?}", s)).collect();
    format!("&[{}]", inner.join(", "))
}

fn fmt_str_slice_slice(v: &[Vec<String>]) -> String {
    let inner: Vec<String> = v.iter().map(|g| fmt_str_slice(g)).collect();
    format!("&[{}]", inner.join(", "))
}
```

**Important:** `phf_codegen` with 461 048 entries (full dictionary) will produce
a very large generated source file and may compile slowly. Verify compile time is
acceptable. If it is too slow, fall back to embedding the JSON bytes and deserialising
into a `HashMap` at WASM init time using `serde_json` compiled to WASM — this
trades zero-init for slower-but-still-fast init, and is a known-working fallback.

## src/lib.rs

```rust
use wasm_bindgen::prelude::*;

pub struct Entry {
    pub p:   &'static [&'static str],
    pub g:   &'static [&'static [&'static str]],
    pub pg:  &'static [&'static str],
    pub pg2: &'static [&'static str],
}

include!(concat!(env!("OUT_DIR"), "/jmdict_map.rs"));

/// lookup(word: string) -> object | null
///
/// Returns an object with the same shape as the current JSON entries:
///   { p: string[], g: string[][], pg?: string[], pg2?: string[] }
/// Returns null if the word is not in the dictionary.
#[wasm_bindgen]
pub fn lookup(word: &str) -> JsValue {
    match JMDICT.get(word) {
        None => JsValue::NULL,
        Some(entry) => {
            let obj = js_sys::Object::new();
            set(&obj, "p",  &to_js_str_array(entry.p));
            set(&obj, "g",  &to_js_str_array_array(entry.g));
            if !entry.pg.is_empty()  { set(&obj, "pg",  &to_js_str_array(entry.pg)); }
            if !entry.pg2.is_empty() { set(&obj, "pg2", &to_js_str_array(entry.pg2)); }
            obj.into()
        }
    }
}

fn set(obj: &js_sys::Object, key: &str, val: &JsValue) {
    js_sys::Reflect::set(obj, &JsValue::from_str(key), val).unwrap();
}

fn to_js_str_array(v: &[&str]) -> JsValue {
    let arr = js_sys::Array::new();
    for s in v { arr.push(&JsValue::from_str(s)); }
    arr.into()
}

fn to_js_str_array_array(v: &[&[&str]]) -> JsValue {
    let arr = js_sys::Array::new();
    for inner in v { arr.push(&to_js_str_array(inner)); }
    arr.into()
}
```

## JS shim and index.html changes

Create `jmdict_shim.js` at the repo root (same pattern as `kuromoji_shim.js`):

```js
// Replaces the fetch-and-parse JMdict load with a WASM lookup function.
// Sets window.jmdictWasm = { lookup } once WASM is initialised.
// index.html's loadJMdict() checks for this and skips the fetch entirely.
(function () {
    const mode = localStorage.getItem('dictionaryMode') === 'ultra' ? 'ultra' : 'full';
    const wasmJs = mode === 'ultra' ? './pkg/jmdict_ultra_wasm.js' : './pkg/jmdict_full_wasm.js';

    import(wasmJs).then(function (mod) {
        return mod.default().then(function () {
            window.jmdictWasm = { lookup: mod.lookup };
        });
    }).catch(function (e) {
        console.error('jmdict-wasm init failed, falling back to JSON load:', e);
        // Leave window.jmdictWasm undefined — loadJMdict() falls back automatically
    });
})();
```

Add to `index.html` before `kuromoji_shim.js`:

```html
<script src="jmdict_shim.js"></script>
```

Modify `loadJMdict()` in `index.html` to use the WASM lookup if available:

```js
async function loadJMdict() {
    if (!COMPRESSION_SUPPORTED) {
        throw new Error('DecompressionStream not supported');
    }

    // Fast path: WASM dictionary already initialised
    if (window.jmdictWasm) {
        jmdict = window.jmdictWasm;  // proxy object — lookup() called instead of []
        jmdictLoaded = true;
        return;
    }

    // Wait briefly in case WASM is still initialising
    await new Promise(resolve => setTimeout(resolve, 0));
    if (window.jmdictWasm) {
        jmdict = window.jmdictWasm;
        jmdictLoaded = true;
        return;
    }

    // Fallback: original fetch-and-parse path
    // ... existing code unchanged ...
}
```

**Important:** The existing lookup code uses `jmdict[word]` (bracket notation). When
`jmdict` is replaced by a proxy or WASM wrapper, this must still work. Two options:

1. **Proxy object:** Wrap `window.jmdictWasm` in a JS `Proxy` with a `get` trap that
   calls `lookup(key)`. Drop-in replacement for the `jmdict[word]` access pattern.
2. **Modify lookup sites:** Change `jmdict[word]` to `jmdict.lookup(word)` (or a helper
   function) throughout `index.html`. More invasive but more explicit.

Recommendation: **Proxy**, since it requires no changes to the lookup logic:

```js
jmdict = new Proxy({}, {
    get(_, word) {
        if (typeof word !== 'string') return undefined;
        const result = window.jmdictWasm.lookup(word);
        return result === null ? undefined : result;
    },
    has(_, word) {
        return window.jmdictWasm.lookup(word) !== null;
    }
});
```

The `has` trap makes `word in jmdict` work correctly; the `get` trap handles
`jmdict[word]`. Both are used by the app.

## Build tooling

### Cargo.toml

Two separate crates under `jmdict-wasm/`:

```
jmdict-wasm/
  ultra/
    Cargo.toml    (name = "jmdict-ultra-wasm")
    build.rs
    src/lib.rs
  full/
    Cargo.toml    (name = "jmdict-full-wasm")
    build.rs
    src/lib.rs
```

Both `build.rs` and `src/lib.rs` are identical; only the `JMDICT_MODE` env var
differs. Consider using a workspace to share the source.

Alternatively, a single crate with a Cargo feature flag:

```toml
[features]
ultra = []
full  = []
```

And `build.rs` reads `#[cfg(feature = "ultra")]` at build time. This is cleaner.

## Correctness tests

Native Rust tests (no browser required):

```rust
// jmdict-wasm/tests/lookup.rs

#[cfg(feature = "ultra")]
mod ultra {
    use jmdict_wasm::lookup_native;

    #[test] fn known_word() {
        let e = lookup_native("食べる").expect("食べる should be in dictionary");
        assert!(e.p.contains(&"v1"), "食べる should be ichidan verb");
        assert!(!e.g.is_empty(), "should have glosses");
    }

    #[test] fn particle_ha() {
        // は has a particle sense with pg glosses
        let e = lookup_native("は").expect("は in dictionary");
        assert!(!e.pg.is_empty(), "は should have pg glosses");
    }

    #[test] fn unknown_word() {
        assert!(lookup_native("ナントカカントカ").is_none());
    }

    #[test] fn pg2_entry() {
        // かな has both pg and pg2
        let e = lookup_native("かな").expect("かな in dictionary");
        assert!(!e.pg2.is_empty(), "かな should have pg2");
    }
}
```

Add `pub fn lookup_native(word: &str) -> Option<&'static Entry>` to `lib.rs`
gated on `#[cfg(not(target_arch = "wasm32"))]`.

## Open questions

### Q1: phf_codegen compile time for the full dictionary

The full dictionary has 461 048 entries. Code-generating a `phf::Map` of that
size may produce a multi-MB `.rs` file and take minutes to compile. **Measure
this before committing to phf.**

If compile time is unacceptable (>5 min), use the fallback: embed the gzipped
JSON bytes as `include_bytes!()`, decompress at WASM init time with the `flate2`
crate compiled to WASM, and deserialise with `serde_json`. This trades zero-init
for ~100–500 ms init (far better than the current 3 s JS parse).

### Q2: WASM binary size

The full PHF map will embed all string data statically. Estimate: the uncompressed
full JMdict is 41 MB; compiled to a PHF with Rust overhead it may be 50–80 MB
uncompressed, 15–25 MB gzip. Measure after first build. If over 30 MB gzip,
consider ultra-compact only, or the `include_bytes!` fallback.

### Q3: Proxy performance

The JS `Proxy` adds a function call overhead on every `jmdict[word]` access.
The app calls this on every morpheme click and during analysis. Profile to confirm
it is not a bottleneck. If it is, change the lookup sites to use a helper function
directly.

### Q4: Initialisation race

`jmdict_shim.js` starts loading the WASM as soon as the script tag is parsed.
`loadJMdict()` is called from `initWithRetry()` shortly after. The WASM may or
may not be ready by then. The shim uses a `setTimeout(resolve, 0)` to yield once,
but if WASM takes longer the fallback JSON path runs. Measure whether the WASM
consistently beats the JSON parse (it should — WASM loads and inits in \<500 ms
vs 3 s for JSON). If not, add a proper `await`-able promise to the shim.
